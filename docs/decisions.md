# Decisions

Choices made where the spec was silent or ambiguous. Conservative, offline, hardware-safe by default (CLAUDE.md). Newest last.

---

### 2026-10-27 — Milestone 0

1. **PstRotator headings are sent as whole degrees.** The documented command only shows an integer (`<AZIMUTH>85</AZIMUTH>`); decimal support is unverified. 294.6° is sent as 295. Revisit after the live test in `docs/rotator-notes.md`.
2. **The spike CLI checks only 0–359.9°.** Per-rotator az min/max and stop position (invariant 7) arrive with rotator profiles in Milestone 2. Until then PstRotatorAz's own limits protect the rotor.
3. **Simulation adapter built in Milestone 0**, ahead of Milestone 1, so `beamnav-rotor --adapter simulation` works without hardware. Owner's decision.
4. ~~**PstRotator reply listener** binds to `127.0.0.1` when the rotator host is loopback (no firewall prompt), otherwise `0.0.0.0`.~~ Superseded by 9. It never uses `SO_REUSEADDR`, which on Windows would let it take a port another program owns.
5. **Simulated rotor travels the numeric path** (stop at north: 350° → 10° goes down through 180°). Placeholder until rotator profiles model the real stop position.
6. **Hamlib reports `has_feedback = True`** because rotctld always answers `p`. Some Hamlib backends may echo the commanded heading rather than a measured one; revisit when a real Hamlib rotor is tested, so the UI never claims a measured position it does not have (invariant 6).

### 2026-10-27 — Deferred from the Milestone 0 review

Not fixed in the spike; each must be resolved by the milestone named.

7. **PstRotator accepts `AZ:` replies from any sender** (`pstrotator.py`, `_await_azimuth`). When listening on `0.0.0.0` for a rotator on another computer, a stray datagram could be shown as measured position (invariant 6). Accept replies only from the configured host. **By Milestone 2** (LAN rotators). Now applies to every PstRotator setup (decision 9). For a loopback host, "the configured host" must also accept this PC's own LAN addresses, since PstRotatorAz replies from one. **Resolved 2026-10-28 (plan 2b Task 1).**
8. **Hamlib can read a late reply as the answer to the next command** (`hamlib.py`, `_read_line` buffer). After a timeout, the stale reply stays queued on the connection. The spike CLI stops at the first failure, so it cannot happen yet. Close and reconnect after any timeout. **By Milestone 2** (long-lived connections). **Resolved 2026-10-28 (plan 2b Task 2):** the connection is closed after any timeout or error and reopened by the next command; the failed command is not resent.

Nits, author's choice:
- `cli.py`: prints `Sent: None` when nothing was sent; say "nothing sent".
- `cli.py`: the `Adapter:` line omits the port.
- `tests/unit/test_cli.py`: assumes the port after a free random port is also free; rare flaky failure.
- `hamlib.py`: `assert` used as a runtime check; raise an error instead.

### 2026-10-27 — Milestone 0 live test

9. **PstRotator reply listener always binds to `0.0.0.0`.** On the live test, PstRotatorAz on the same PC as `beamnav-rotor` sent the `AZ?` reply from and to the LAN address (`192.168.2.195`), not loopback, so the `127.0.0.1` listener never saw it. The listener is open only while waiting for one reply (default 2 s). Still no `SO_REUSEADDR`. Test: `test_reads_reply_sent_to_lan_address`.

### 2026-10-27 — Milestone 1a (geometry and targets)

10. **The operator states their home region.** With no region polygons in v2 (requirements 4.2), "You are in NJ" cannot be computed from a grid. `lookup()` takes `home_region`; the CLI has `--home-region`, and the operator profile will hold it (plan 1c). Without it, a region target gets a normal bearing. Owner's decision.
11. **Region centroids** come from Natural Earth 1:50m admin-1 v5.1.2 (public domain), as area centroids in a cylindrical equal-area projection (`tools/build_regions.py`). Canadian territories are left out; the spec names provinces only. From FM29pt, MD comes out at 245.7°, inside the spec's 243° ±3 but near its edge.
12. **Built-in names win over aliases.** Headings, compass points, grids and region codes are matched before aliases, so an alias named `NC` cannot silently turn North Carolina into something else. The store (plan 1c) must refuse alias names that collide with a built-in.

### 2026-10-27 — Milestone 1c (store)

13. **A roster fills gaps in a station record but never changes it.** A station first seen in a roster gets a record with `source='roster'`. A later roster may fill that record's empty name, grid or QTH (a DMR net has no grids; the next 2 m net does), but never overwrites a value already there, and never touches a record the operator saved. Differences are flagged as conflicts and kept in each check-in's snapshot (spec 7: change no saved record silently). Whether a newer roster grid should *replace* an older roster grid: the operator is asked (decision 40).
14. **Replacing an imported session is limited to an import of the same net and date.** Any other id is refused before anything is deleted (invariant 9).

### 2026-10-27 — Milestone 2a (rotator profiles and the Rotate path)

15. **Each rotator profile describes its own travel.** Rotators differ (owner: Yaesu rotors turn 450°), so a profile has a travel range in rotor degrees and an offset, with presets for north stop 0–360°, south stop 180–540° and Yaesu 450° (0–450°). A true heading may be reachable at two rotor positions in an overlap; with a known position the nearer one is taken, otherwise the lower one and the path is marked unverified. Outside the travel is rejected, never wrapped. Hamlib and simulation are sent the rotor position; PstRotatorAz's documented command takes 0–359 only, so it is sent the position mod 360, it chooses the path itself, and the plan says so. Live test row 5 in `rotator-notes.md` will show what PstRotatorAz actually does.
16. **The Rotate service keeps one adapter per rotator**, rebuilt when the profile changes, so a simulated rotor remembers its position between presses.
17. **A connection test passes only on a real answer** when the rotator reports position: a UDP "connect" proves nothing (Milestone 0 finding). It never moves the rotator.

### 2026-10-28 — Milestone 2b (dashboard and settings)

18. **Bands are a table, each served by at most one rotator.** Migration 0003 seeds 10 m (28 MHz), 6 m (50), 2 m (144), 1.25 m (222), 70 cm (432), 33 cm (902) and 23 cm (1296), with long path on for 10 m and 6 m (spec 4.1). The operator can add bands (microwave), delete unused ones, and toggle long path. The nominal MHz feeds the coarse-location note. A rotator's bands must name rows of this table, and a band served by one rotator cannot be claimed by another, so that rotator is the band's default with no ambiguity. The dashboard can still pick any rotator before Rotate (spec 4.7).
19. **The Rotate preview plans from the last position read this session.** `RotateService` remembers the rotor position from the read before each move, the read after it, and every explicit Read position press. A preview with no known position says the path is unverified, never a guessed direction. A PstRotatorAz preview never states a direction (decision 15).
20. **Rotator I/O runs on the UI's event loop.** One `sqlite3` connection is used from one thread, and a rotator call blocks for at most its timeout (2 s). Progress polling only reads. A worker thread can come later if the pause matters in use.
21. **Hotkeys come with the live net screen (plan 2c).** That includes the Rotate hotkey and the number-pad sector keys. Until then Rotate is a button press only, which satisfies invariant 2.
22. **Hotkey defaults and safety.** `Ctrl+Enter` rotates to the displayed target on the dashboard and the live net screen. On the live net screen, `Home` snaps back to the controller and the number-pad keys announce sectors (8 N, 9 NE, 6 E, 3 SE, 2 S, 1 SW, 4 W, 7 NW, matched by key code so the top-row digits do nothing). Remapping: decision 33. No hotkey acts while a text field, select, textarea or button has focus, so Ctrl+Enter can never also "click" a focused button. Buttons drop focus after a click, so the keys work right after one. Auto-repeat is ignored twice over: the browser does not send it, and `hotkeys.action_for` refuses it. A held key therefore sends at most one command (invariant 2).

### 2026-10-28 — Milestone 3a (net control)

24. **Check-in times are shown in the net's own time zone.** The order is the net's time zone, then the active profile's, then this computer's. A name that is not a real zone is skipped, never guessed. Times are stored in UTC. On Windows the named zones come from the `tzdata` package, which the owner approved as a runtime dependency on 2026-10-28. (First version, same day: this computer's local time only, until `tzdata` was approved.)
23. **Entry-line keys follow contest loggers.** Fields: Callsign → Name → Grid → QTH → Report → Notes. `Tab` and `Shift+Tab` move between fields, `Enter` logs from any field, and `Esc` clears. `Space` moves on only from Callsign and Grid, where a space can never be typed; in Name, QTH, Report and Notes it types a space (spec 4.5 says "Space/Tab next field"; "MARY ANN" must still work). `ArrowDown`/`ArrowUp` in Callsign move through the partial-call list, and `Ctrl+N` adds a station note (`Alt+N` since decision 38). Remapping: decision 33.
25. **Net schedules.** Weekday 0 = Monday (Python's numbering); files use day names. Start time is HH:MM in the net's zone (decision 24 order). An unknown zone is refused when a net is saved. Next occurrence is the first weekday-and-time at or after now.
26. **`*.beamnet.json` shares net definitions only** (schema 1, Design section of plan 3b): no ids, archive flag, rotator or history. Import adds new nets and never overwrites one with the same name (ignoring case); a bad net is skipped with its reason; a bad file imports nothing.
27. **Example nets come from the owner's schedule (docs/example-nets-source.txt, 2026-10-28)** and hold only what it states: no guessed zones, modes or durations. The four Monday Pack Rats controllers are the calls the schedule pairs with each net, and the owner's own rosters (tests/fixtures) mark each of them as net control; the other nets have no controller. They are offered once on the nets page, opt-in, and flagged unverified until the operator ticks "I've checked these details".
28. **Online callsign lookup is now an optional requirement (owner, 2026-10-28; requirements 4.9).** QRZ XML Data first, with the operator's own subscription. The QRZ login is stored with `keyring` (the operating system's credential store), which the owner approved as a runtime dependency the same day. Offline-first still holds: lookups only add data, and the app works the same without a connection.
29. **QRZ lookups follow spec 1.34 (tests/fixtures/qrz_xml_spec_1.34.txt).** HTTPS POST, so the password is never in a URL; one session key kept in memory; one re-login on Session Timeout and no retry loop; "Connection refused" stops lookups until restart. Location precision comes from geoloc: user/grid and geocode positions can be used (the latter noted as a postal address), zip/state/dxcc are shown only as approximate and never offered as a grid. Results are cached in their own table, apart from station records, and fill only blank fields on the controller screen. The login lives only in keyring.
30. **QRZ lookup is automatic unless data is stored (owner, 2026-10-29).** Entering a callsign on the dashboard or controller screen looks it up on QRZ when there is no saved grid for it and no earlier QRZ answer; a saved record without a grid still gets a lookup, which fills only blank fields. On by default; Settings → QRZ can switch it off (`qrz_auto` = "off"). With no saved login or no credential store, the automatic lookup is silent; a press of Look up on QRZ still reports why. The lookup is started by the keypress (on the controller, deferred by a one-shot timer so typing is not held up) and never sends a rotator command.
31. **QRZ answers are used, and Enter in Callsign fills first (owner, 2026-10-29).** After testing with K2TXB the owner asked that the dashboard drop the "Grid needed" box when QRZ knows the station, that the QRZ button read like "Save this station", and that Enter or Tab in Callsign fill Name, Grid and QTH. So: a call with no saved location uses an exact QRZ position (station or address precision) for the bearing, labelled QRZ, while the lookup runs the dashboard says "Looking up … on QRZ…"; **Save this station** fills the station record's blanks only (source saved; a QRZ position without a grid is kept as lat/lon); approximate answers keep the Grid needed box and the Show approximate bearing button. On the controller, a cached QRZ answer fills blanks with no new lookup, and the first Enter in Callsign fills and moves to Name instead of logging; the next Enter logs. This replaces the spec 4.5 rule that a single Enter in Callsign logs. Entry boxes are wider and the line wraps. Later the same day, after trying K2WB, the owner asked that **Look up on QRZ** open the station's QRZ.com page in the browser: it is now a plain link to `https://www.qrz.com/db/<CALL>` in a new tab (no XML lookup, no login sent), so the XML lookup happens only automatically. Name is wider and QTH moved to the entry's second line with Report and Notes; on a narrow window the info panel drops below the entry line. The session table's cells widened to match (Name 20 rem, QTH 12 rem; they no longer shrink, and a narrow window scrolls the table sideways). The controller's QRZ link is redrawn whenever the callsign changes, because a browser ignores a link added to a button it has already drawn.
32. **Example nets bring their participants (owner, 2026-10-29).** The owner added a 14th example net in a message ("Packrat DMR Net Monday night 7pm New control george KA3WXV Talkgroup 8803", corrected to 8804): Monday 19:00, Talkgroup 8804, mode DMR, controller KA3WXV with no grid given. The owner's six rosters (copied byte for byte from tests/fixtures into package data, with a manifest naming each one's net and date) are imported as past sessions of their example nets when the operator presses Add examples, through the normal roster import, so their 54 stations become roster records that never overwrite a saved one; a net the operator already had under an example name gets no session. After that, if a QRZ login is saved and automatic lookup is on, the example stations missing a name or grid are looked up once, one at a time, in the Nets page's own task: answers go to the QRZ cache only (decision 29), "not found" moves on, the first other failure stops the pass with one message, and no login means no lookups and no message. Cached answers then fill blanks on the controller screen and give exact positions on the dashboard (decision 31).
33. **Every shortcut can be changed in Settings → Keys (spec 4.5; plan 3d).** Seventeen actions in two groups: the dashboard and live net (Rotate, Snap back, the eight sector keys) and the net-control entry line (next, previous, log, clear, station note, next/previous suggestion). Keys are matched by physical key code, and a chord on Enter also matches the number-pad Enter. Only the operator's changes are saved, as JSON in the `keymap` setting; anything unreadable, unknown or now clashing falls back to its default, and Settings says so. A new key is refused when it clashes in its group, would type a character on the entry line, is Tab for a dashboard key, is kept by the browser (Ctrl+W, Ctrl+T, Ctrl+Tab, Ctrl+Shift+Tab, Ctrl+L, Ctrl+R, F5, F11, F12, Alt+F4), or is a modifier alone. To record a key the operator presses Change then the key; Escape cancels, so Escape returns only through Reset. Space moving on from Callsign and Grid stays fixed (decision 23). Chords match exactly, so Ctrl+Shift+N is no longer a station note. A remapped Rotate is still one fresh keydown (invariant 2). No on-screen text names a key yet, so nothing else needed updating. After the final review: the number-pad Enter is stored as Enter, so it can never hide a clash; the saved changes are resolved as a whole, so a swap made in two steps is kept, and a reset that would clash is refused with the reason; Rotate and Snap back (the keys that move the rotator) need Ctrl or Alt, or a key that never types and does not work a control (F-keys, Home, End, Insert, Page Up/Down, number pad), because a plain letter, Space, Enter or arrow could fire while a dropdown has focus — announcing a sector never moves the rotator, so sector keys may be plain; the dashboard and live net read the keys on every press, and an already-open net control page asks for a reload instead of acting on outdated keys. The owner confirmed the rotator-key rule and the fixed Space on 2026-10-29.
34. **Backup and restore are one database file (spec 4.8; plan 4a; owner approved the design 2026-10-29).** Settings → Data → Back up downloads an exact SQLite copy, `beamnav-backup-YYYY-MM-DD-HHMM.db`. The QRZ login is not in it: it lives only in the credential store (acceptance test 35). Restore checks the whole file in memory first and changes nothing if it is not a Beam Navigator database, is damaged, or comes from a newer app; an older one is migrated. After the operator confirms, the current data is kept as `backups/before-restore-YYYY-MM-DD-HHMMSS.db` in the data folder (never overwritten, never pruned), and the backup replaces it in place. Every rotator comes back in simulation with its connection test cleared, because the backup may come from another PC and live mode needs a test passed on this one (invariant 8); remembered rotor positions are forgotten, and no rotator command is sent (invariant 2). The owner asked that the operator be told the rotator is in simulation: the confirmation dialog says so before the restore, and the success notice, which stays until closed, says so again. After the final review: a backup must hold exactly the tables and indexes this app makes, so a trigger or view from a crafted file can never be copied in (one could have put a rotator back in live mode); a full disk, locked file or read-only folder during a restore gives "Couldn't restore: … Nothing was changed."; and the Settings page reopens itself after a restore, on the Data tab with the notice, so no panel keeps showing old data such as a rotator still marked live. A rotator that is turning during a restore keeps turning: Stop then goes to the simulator, and the controller's own stop still works (requirements 4.7).
35. **A Welcome wizard shows until a station is active (Milestone 4; plan 4b; owner, 2026-10-29).** Opening the dashboard while no operator profile is active (none saved, or saved but none active, at the owner's request) goes to `/welcome`, a three-step wizard: Your station, Example nets, Next steps. **Skip for now** opens the dashboard for that visit only; the wizard comes back next time, until a station is active. Also at the owner's request, step 1 is filled with the operator's last wizard entries (kept in the `welcome_draft` setting on every Next, even a refused one, and on Skip), or else from the most recently saved profile, which Next then updates instead of duplicating; saved profiles are also listed with a Use button. A time zone must be one `zoneinfo` knows. Step 2 answers the example-nets offer (requirements 4.6) through the Nets page's own add and decline, so it is asked once; it does not start the example stations' QRZ pass, which the Nets page still runs. Step 3 links to Settings → Rotators, QRZ and Keys (`/settings?tab=…`), and step 1 links to Settings → Data for a restore. The wizard never creates a rotator profile, sends a rotator command or goes online. After the final review: when the form is filled from a saved station it says "Editing <name>" and offers New station instead, so a saved station is never changed unnoticed; a changed grid drops that station's old exact position and state, so bearings come from the new grid (invariant 3); and a new station whose name (its callsign, or Home) is already taken is refused with the reason instead of failing silently. "Most recently saved" means the newest profile (highest id).
36. **The Windows program is one PyInstaller file (spec 8; plan 4d; PyInstaller approved as a dev tool by the owner 2026-10-29).** `uv run python packaging/build_windows.py` builds `dist/BeamNavigator.exe` (about 37 MB, about 40-70 s) from `packaging/beamnav_entry.py` with `--onefile --collect-all nicegui --collect-data beam_navigator --collect-data tzdata --hidden-import keyring.backends.Windows`; a trial build on the owner's PC proved these options: the program created the database, ran the Welcome wizard, loaded all 14 example nets with their 6 rosters, and read the QRZ login from Windows Credential Manager. It uses the same data folder as `beamnav-ui`. Started on a port already in use (usually a second double-click), it says so with the address of the running copy, waits for Enter when it is the program (not when there is no keyboard), and exits with code 1 instead of a traceback. `--no-browser` starts it without opening a tab. `tests/packaging/test_exe_smoke.py` runs the built file on a throwaway folder only when `BEAMNAV_EXE` names it; it removes pytest's variables first, because NiceGUI otherwise expects its test harness. Building needs the app stopped, because Windows locks a running program's files. After the final review: on Linux, macOS and the Pi the port check binds the way the server does (address reuse on), so restarting right after quitting is not wrongly refused; on Windows it stays off, because there it would let a second copy share the first one's port.
